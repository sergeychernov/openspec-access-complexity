# Proposal

## Why

После OpenSpec propose владелец выбирает модель для apply и verify без сопоставимой оценки объёма, сложности, риска и нагрузки на лимиты. Нужен переносимый skill с объяснимыми рекомендациями, воспроизводимым расчётом и сохраняемой историей оценки внутри change.

## What Changes

- Добавить общий `SKILL.md` для Codex, Claude Code и Antigravity IDE: агент составляет структурированный профиль с evidence, а Node.js `.mjs` выполняет валидацию и расчёт.
- Разделить оценку самого change и пригодность моделей. Учитывать объём, домены и связи, слои, архитектуру, логику, совместимость, проверяемость, последствия ошибки и неопределённость.
- Формировать четыре отсортированных списка: apply/API, verify/API, apply/subscription и verify/subscription. Среди вариантов с достаточным качеством минимизировать прогнозируемый расход с небольшой поправкой на типичное время: до 30 минут без штрафа, далее линейно +5% за каждые дополнительные 30 минут. Не обрезать различия больших расходов. Показывать рекомендуемый effort, исходные прогнозы, поправку, основания и ограничения; окончательный выбор остаётся за владельцем.
- Поставлять редактируемый каталог последних проверенных версий указанных десяти семейств моделей и конфигуратор матрицы «параметр × модель» отдельно для apply и verify. Для каждого supported effort задаются самостоятельные оценки и resource-настройки с основаниями; универсальная прибавка к базовому качеству не используется. Версии и коэффициенты обновляются вручную.
- Показывать модельные оценки по шкале 0–100, понятные подписи и подсказки для важности параметра и оценки модели. Использовать компактные буквенные индикаторы происхождения с общей легендой и доступными подробностями источника. В допускающих unknown полях очистка значения означает «Нет данных»; отдельная кнопка ∅ или меню для этого не нужны.
- Хранить benchmark snapshot с источниками; явно отличать независимые измерения, proxy, эвристики, unknown и пользовательские overrides. Для числового коэффициента показывать исходные данные и правило преобразования; ссылка на общий рейтинг без такого правила не делает эвристическое значение proxy или measured. Не заявлять доказанную оптимальность или вероятность успеха по эвристическому баллу.
- Сохранять профиль, отчёт и эффективные входы расчёта в `assessment/` внутри разрешённого OpenSpec change. При archive они переходят вместе с change; replay использует сохранённые входы, а не текущие defaults. Разделить миграцию прежнего формата base + effort delta с сохранением результата при неизменной политике и явное включение новой политики выбора, которое может менять рейтинг. Исторические snapshots не переписываются.
- Добавить пример полного цикла и проверки воспроизводимости, stale detection и архивирования. Подготовить документацию для самостоятельного распространения пакета и воспроизведения результатов читателями.

## Capabilities

### New Capabilities

- `change-assessment-profile`: доказательный профиль change, структурная валидация, снимок исходных артефактов и оценка сложности независимо от моделей.
- `model-suitability-ranking`: детерминированные рекомендации для фаз apply/verify и режимов API/subscription, объяснение результатов и работа с неопределённостью.
- `assessment-configuration`: каталог моделей, происхождение коэффициентов, пользовательские настройки и локальный конфигуратор.
- `openspec-assessment-lifecycle`: переносимый skill, интеграция после propose и перед verify, хранение и воспроизведение оценки в активном и архивном change.

### Modified Capabilities

Нет: target specs пока отсутствуют; все четыре capabilities вводятся этим change. Начальная реализация уже существует, согласованные уточнения учитываются отдельными задачами доработки.

## Impact

На момент начала change репозиторий содержал инициализированный OpenSpec и generated skills. Начальная реализация самостоятельного пакета уже находится в `packages/openspec-assess-change/`: Node.js CLI, JSON-контракты, локальный конфигуратор, документация и тесты. Уточнения затрагивают config/override contracts, defaults, evaluator, интерфейс, отчёты и миграцию; завершённые задачи сохраняют историю, новая работа отмечается отдельно. Клиенты подключают одну версию пакета; scorer не зависит от их SDK и не вызывает модель.

Область change — подготовка профиля и рекомендации. Запуск apply/verify, автоматическая смена модели, dispatcher, публикация GitHub/npm и статья на Habr остаются отдельными действиями. Upstream skills OpenSpec не редактируются вручную; профиль хранится как дополнительный артефакт change без подмены статусов задач и приёмки.

# Design

## Context

Репозиторий содержит OpenSpec spec-driven, generated skills и реализацию в `packages/openspec-assess-change/`. Основание change — [proposal.md](proposal.md). Дизайн описывает итоговый контракт с уточнениями конфигуратора и политикой выбора. Реализованы отдельные effort-записи и minimum-resource-with-time-penalty; новая доработка касается компактности интерфейса, читаемости подсказки веса и числового ввода множителей. Существующие конфигурации и snapshots учитываются при миграции; отметки прежних implementation tasks не означают выполнения новых требований раздела 11 tasks.md.

Подтверждены: общий SKILL.md и .mjs, агент готовит evidence-профиль, четыре рейтинга, ручное обновление моделей, отдельный распространяемый пакет, сохранение профиля внутри change и архивирование вместе с ним. Последние проверенные названия моделей относятся к 2026-11-14; наличие модели у конкретного аккаунта задаётся отдельно.

## Goals / Non-Goals

**Goals:** расчёт offline по явным входам; минимизация расхода среди достаточно качественных вариантов с небольшой поправкой на время; объяснимая настройка; переносимость; воспроизводимость исторических результатов; контролируемая семантика unknown.

**Non-Goals:** автоматический выбор модели в клиенте, вызовы inference, обучение router, диспетчеризация workers и прогноз точного остатка подписки без наблюдений. Skill не заменяет OpenSpec verify и приёмку. Подготовка публикации репозитория или статьи не является побочным эффектом assess.

## Decisions

### 1. Общий пакет и граница агент — evaluator

Один пакет содержит SKILL.md, schemas, scripts, evaluator, config, configurator, references и examples. CLI и локальный configurator используют одну pure ESM-библиотеку расчёта; Node-specific I/O расположен отдельно. Рабочий код — .mjs, без обязательной компиляции TypeScript и без SDK клиентов. Node.js — единственный runtime пакета, OpenSpec CLI нужен для интеграции с change. Поддерживаемые версии закрепляются в package metadata и CI при реализации.

Агент читает planning-артефакты и релевантные исходники, заполняет профиль по описанным якорям шкалы и приводит evidence. Скрипт проверяет структуру, локальные ссылки и digest, но не объявляет семантическое суждение агента доказанным. CLI не обращается к LLM. Поэтому детерминизм обещается для закреплённых входов, а не для независимого повторного чтения prose разными агентами.

Альтернатива «оценить всё регулярными выражениями» не выбрана: число файлов и keywords не передаёт смысл архитектуры. Свободная LLM-сортировка не выбрана, поскольку она не обеспечивает воспроизводимость.

### 2. Контракт профиля

Версия schemaVersion задаёт стабильные factor IDs. Профиль хранит change identity, stage planning/verification, scope задач, исходные evidence references и факты. Fact kinds: measured, declared, estimated; состояние значения: known, unknown, not-applicable. Evidence включает относительный путь, идентификатор Requirement/задачи или диапазон строк, digest доступного источника, основание оценки; revision указывается, когда известна.

Основные группы:

| Группа | Пример структуры |
| --- | --- |
| Объём | tasks, предполагаемые или фактические файлы, диапазон diff, generated-файлы отдельно |
| Домены | перечень domain IDs, границы и существенные связи |
| Слои | множество категорий и пересечения границ |
| Архитектура | новые компоненты, изменение контрактов, ответственности и зависимостей |
| Логика | алгоритмы, state machines, concurrency, distributed state |
| Совместимость | public API, schema/data migrations, backward compatibility |
| Проверяемость | тестовые oracles, воспроизведение, integration/runtime-зависимости |
| Последствия | security, данные, blast radius, обратимость |
| Неопределённость | незакрытые решения, неизвестные зависимости, неполнота acceptance criteria |

Для применимых оценок используется шкала 0–4 с конкретными якорями для каждого factor. 0 означает минимальную трудность применимого фактора; отсутствие фактора задаётся not-applicable с основанием. Количественные факты преобразуются в уровни через явные thresholds. Слой не получает универсального балла «frontend проще infrastructure»: оцениваются требования к навыкам и переходы между границами.

Выходные свойства change — отдельные volume, complexity, risk и uncertainty, а не одна непрозрачная сумма. Для численных индексов используется взвешенная нормализация в диапазон 0–10000 basis points. Неизвестная сложность даёт нижнюю и верхнюю границу (0 и 4 для неизвестного уровня), а не искусственное нулевое значение. Прогноз количества файлов или токенов остаётся диапазоном; он не становится P90 без измеренной выборки.

### 3. Конфигурация и начальный каталог

Слои конфигурации: поставляемые defaults → явно переданные user overrides. Merge выполняется по стабильным IDs и известным schema keys. Отсутствие наследует значение; 0 и false являются значениями; unknown задаётся отдельным статусом. Полученный effective config проверяется целиком и сохраняется в snapshot.

Разделяются общие complexity weights, phase relevance weights, matrix параметр × модель/effort, hard constraints, quality thresholds, resource profiles и selection preferences. Пользователь может менять каждый модельный коэффициент для apply/verify; происхождение override сохраняется. Формат не содержит исполняемого JavaScript.

Единица настройки качества — версия модели + harness + фаза + factor + supported effort. В новой версии config/override contracts канонической становится полная матрица `byEffort[effort][factor]`: отдельная запись со значением в целых basis points и provenance. Каждый supported effort, включая временно выключенные из рекомендаций, имеет все factor IDs для обеих фаз. Известное значение — целое 0–10000; unknown — явный null со статусом и основанием. Отсутствующая запись является ошибкой структуры; отсутствующие данные представляются записью unknown. Частичный override наследует только ту же конкретную запись defaults, а не соседний effort или фазу.

Новый evaluator не восстанавливает качество через `base + effortDelta`, интерполяцию или универсальную прибавку. Таблицы defaults задают каждую комбинацию явно. Одинаковые значения у разных efforts допустимы; монотонный рост качества не является ограничением. Значения, полученные из общих приоров, остаются heuristic с описанным основанием; явная таблица сама по себе не создаёт измерений. Supported effort IDs сохраняют названия провайдера и не означают сопоставимости одинаковых слов между моделями.

Редактирование численного значения создаёт user-override для выбранной записи и сохраняет отдельное исходное основание: прежнее значение, статус, sources и исходную идентичность. Очистка допускающего unknown поля создаёт unknown/null с собственным основанием и также сохраняет предыдущую запись отдельно. Reset восстанавливает выбранную запись defaults вместе с её provenance. Новая schema явно отделяет исходное основание от текущего пользовательского объяснения, чтобы ссылка на измерение не приписывалась произвольно изменённому числу.

Стартовые семейства и версии:

| Agent | Семейство | Версия |
| --- | --- | --- |
| Codex | Astra | GPT-6 Astra, gpt-6-astra |
| Codex | Sol | GPT-6.1 Sol, gpt-6.1-sol |
| Codex | Terra | GPT-6.1 Terra, gpt-6.1-terra |
| Codex | Luna | GPT-6 Luna, gpt-6-luna |
| Claude Code | Opus | Claude Opus 5.5 |

В каталоге реальные client IDs и supported efforts подтверждаются по первичным источникам перед включением; неизвестный идентификатор не синтезируется из display name. Для новых версий пользователь меняет config вручную. Старые коэффициенты разрешено переносить с отдельной пометкой inherited и сохранением исходной идентичности. Измерение прежней версии не становится measured для новой; proxy требует документированного mapping. Эвристика без такого mapping остаётся heuristic с inherited, а пользовательское изменение — user-override с сохранённым исходным основанием.

Источники идентичности моделей: [OpenAI](https://developers.openai.com/api/docs/models), [Claude Code model configuration](https://code.claude.com/docs/en/model-config), [Antigravity models](https://antigravity.google/docs/models). Публичная доступность не означает наличие подписки или остатка у пользователя.

Альтернатива динамическому latest отклонена: она изменила бы результат без изменения config. В каталог не добавляются другие семейства автоматически.

### 4. Benchmark evidence и калибровка

benchmarks.json хранит небольшие структурированные records с URL, датой, benchmark version, точными model/harness/effort, metric, score, единицами, числом attempts и uncertainty при наличии. Повтор одного измерения в нескольких источниках не увеличивает его вес. В отчёт включаются ссылки и атрибуция; тексты статей, закрытые datasets и содержимое benchmark tasks не копируются.

Основания для начальной настройки:

- [Artificial Analysis: методология](https://artificialanalysis.ai/methodology/coding-agents-benchmarking/) и [результаты](https://artificialanalysis.ai/agents/coding-agents): качество, per-task usage, время и API cost вариантов агентов.
- [SWE-bench](https://www.swebench.com/): репозиторные исправления; предпочитать сопоставимый harness и результаты, выполненные или проверенные авторами benchmark.
- [Terminal-Bench](https://www.tbench.ai/): инструментальные и terminal-задачи; версии benchmark не смешивать без явного mapping.

Соответствие benchmark → factor является отдельным версионированным mapping. Измерение общей реализации не становится measured-коэффициентом архитектуры или verify автоматически. Нет сопоставимых данных — явный proxy, консервативная heuristic с rationale либо unknown. Поставляемый baseline должен работать для всех десяти семейств, но не выдавать эвристики за независимые измерения. Пользовательские завершённые changes могут дать локальную калибровку позже; автоматическое обучение вне v1.

Provenance относится к числу конкретной записи, включая effort, а не только к модели в целом:

- measured — сопоставимое независимое измерение точной версии/harness/effort и данной категории; нормализация метрики описана;
- proxy — число получено по явному mapping из связанного измерения с указанием различий и преобразования;
- heuristic — выбранный приор или оценка без воспроизводимого вывода этого числа из измерения;
- user-override — явное пользовательское изменение с отдельным исходным основанием;
- unknown — численного значения нет.

Карточка основания показывает источники и дату, исходные model/harness/effort, benchmark version, метрику и результат, условия и правило преобразования в отображаемую оценку. Для heuristic и unknown вместо отсутствующих измерений показывается rationale; для пользовательского значения — текущее объяснение и исходная запись. Ссылка на общий benchmark, подтверждающий только порядок моделей, не превращает выбранное по tier число 82 в proxy. Общий coding score и результат при max effort не объявляются прямым измерением architecture/verify или low effort. Свидетельства, поддерживающие общее предположение, можно показывать отдельно от источника самого числа.

Правила измерений и provenance защищают от ложной точности, а не гарантируют оптимальность на каждом проекте. Нормализация не зависит от набора включённых моделей: добавление кандидата не меняет коэффициенты остальных.

### 5. Расчёт и сортировка

Числа для quality и weights представлены целыми значениями; денежные величины — целыми микроединицами с явно заданной валютой. Для произведений/делений используются безопасные целые или BigInt. Уже определённые прогнозы и suitability используют закреплённое округление вниз; новый критерий расхода сравнивается как точное рациональное число до округления отображения. Входные decimal-значения нормализуются по schema; NaN, infinity и неоднозначные значения запрещены.

Порядок расчёта:

1. Проверить profile/config/evidence и получить canonical input identity.
2. Рассчитать свойства change независимо от моделей.
3. Развернуть enabled model + harness в допустимые effort variants.
4. Применить известные ограничения контекста, tool capabilities, scope, доступности и бюджета. Невыполнимое ограничение исключает; неизвестное критическое ограничение оставляет provisional.
5. Рассчитать phase suitability и требуемый quality floor, затем ресурсы.
6. Отсортировать variants, выбрать один рекомендуемый effort для каждого model + harness и показать остальные в деталях.
7. Сформировать четыре списка и explanation trace.

После выбора effort evaluator читает ровно соответствующую запись качества; изменение одной записи не затрагивает другие фазы, факторы и efforts. Unknown сохраняет прежнюю семантику coverage/provisional. Explanation trace содержит точную идентичность записи, её значение, происхождение и вклад без скрытой effort delta.

Для известных применимых factor уровней d_i (0–4), phase weights w_i и model coefficients c_i (0–10000):

- relevance r_i = w_i × max(1, d_i);
- suitability F = floor(sum(r_i × c_i) / sum(r_i));
- not-applicable исключается; неизвестная активная model coefficient не заменяется нулём и не даёт полного F;
- unknown d_i использует явно закреплённый консервативный уровень для предварительного подбора и остаётся помеченным unknown в отчёте;
- quality floor выбирается из config по верхней границе сложности/риска; отдельные критические ограничения не растворяются в среднем F.

Полностью известный F — heuristic fit score, не probability. При неполных коэффициентах показываются known contributions и coverage; кандидат остаётся provisional. Нулевая сумма применимых relevance означает «рейтинг не определён», не искусственный tie.

### 5.1. Достаточное качество и минимальный расход

Новая политика выбора `minimum-resource-with-time-penalty` заменяет взвешенную utility. Quality floor и critical factors остаются обязательными условиями допуска. После их прохождения более высокий F не компенсирует больший скорректированный расход; качество используется только при равенстве экономических критериев. Для модели выбирается лучший разрешённый effort по тому же comparator, которым затем сравниваются модели. Сильный вариант может выиграть, когда слабый не проходит требования; низкий effort допустим, когда его качества достаточно.

Обозначения:

- C — верхний прогноз исходного расхода: API `highMicros` в выбранной валюте или subscription `highLoad` в относительных единицах; выбор сценария расхода остаётся прежним;
- T — типичный прогноз времени `typicalMinutes`; верхняя оценка времени остаётся видимой как риск задержки, но не подменяет T;
- g — время без штрафа, default 30 минут;
- s — интервал начисления, default 30 минут, строго положительный;
- k — относительная надбавка за интервал, default 0.05 (500 bp), неотрицательная;
- S — скорректированный расход для сравнения, меньше означает предпочтительнее.

    over = max(0, T - g)
    S = C × (1 + k × over / s)

Параметры политики явно хранятся отдельно для API/subscription, поставляются с одинаковыми defaults и редактируются с пояснением единиц. Они не заменяют phase relevance weights. Период без штрафа неотрицателен; k = 0 явно отключает влияние времени. Для default-настроек 0–30 минут дают ×1, 45 минут — ×1.025, 60 — ×1.05, 90 — ×1.10, 150 — ×1.20. Надбавка непрерывная линейная: без округления количества интервалов вверх и без сложных процентов. Значения T внутри периода без штрафа не участвуют даже в tie-break.

C и S не переводятся в насыщаемую шкалу 0–10000. Никакие cost/load/time anchors не обрезают их сверху; при одинаковом времени рост C строго ухудшает S в допустимом диапазоне данных, в том числе выше прежних $20 или 1000 единиц нагрузки. Добавление другого кандидата не меняет индивидуальный S. Более высокий F не уменьшает S и учитывается только при равных S и C.

При default-параметрах и целых минутах S = C × (600 + over) / 600. В общем случае числитель равен C × (10000 × s + kBp × over), знаменатель — 10000 × s. Сравнение использует точную рациональную арифметику/BigInt без потери дробной надбавки у небольших расходов и без небезопасного Number-произведения. Машинный trace сохраняет точное представление в сериализуемых целых значениях; отображение может округляться отдельно. Равенство отображаемых сумм не создаёт искусственный tie.

S — критерий ранжирования, а не прогноз реальной оплаты или списания квоты. Исходные low/typical/high cost/load/time показываются отдельно. API budget и quota checks используют реальные исходные прогнозы как прежде; штраф не увеличивает billable usage, заявленную стоимость или расход квоты.

### 5.2. Неизвестные данные и стабильный порядок

Порядок групп остаётся eligible → provisional → below-threshold; исключённые перечисляются отдельно. В eligible первыми идут варианты с полными данными для S. Они сортируются по возрастанию точного S, затем исходного C, затем по убыванию F и по стабильным candidate ID/effort ID. Дополнительный tie-break по времени не вводится. Неполные eligible-варианты показываются после полных с доступным F и ID и явной пометкой отсутствующего экономического сравнения.

Если C или необходимый T неизвестен, S не вычисляется: unknown не превращается в нулевой расход, 30 минут или отсутствие штрафа. При явно отключённом k время для S не требуется. При положительном k неизвестный T остаётся неизвестным и для C = 0; отсутствие прогноза не маскируется арифметическим нулём. При полностью известных нулевом C и T формула сохраняет нулевой S, как обычное допустимое значение.

Рекомендация новой политики требует eligible-варианта с известным S. Если таких нет, отчёт сообщает, что экономический выбор не определён имеющимися данными, и показывает варианты для ручного уточнения без объявления самого качественного экономически оптимальным. Отсутствие подходящих по качеству вариантов и отсутствие экономических данных — разные причины.

В provisional сначала идут кандидаты с известным F (по убыванию F), затем без F (по ID); below-threshold сортируется по убыванию известного F и ID. Provisional не получает рекомендацию по экономичности; этот порядок маркируется как предварительный. Исключённые сортируются по ID, а не порядку обнаружения причины. Stable string order использует code units, не localeCompare.

Trace показывает F и порог, результаты critical checks, выбранные записи качества/ресурсов, C, T, параметры штрафа, превышение периода, множитель, точный S, причины неполноты и ключи сравнения. Preview объясняет, почему более экономичный или меньший effort победил при достаточном качестве. Прежние quality/economy/time weights и anchors относятся только к legacy policy и не отображаются как действующие настройки новой политики.

### 6. API и подписки

Для API прогноз определяется явными workload/resource profiles по фазе, категории и effort: нижняя, typical и верхняя оценка billable usage и возможных доработок. Это сценарные оценки, пока нет калибровки на собственных задачах. Pricing adapter складывает непересекающиеся billing categories: uncached input, cache read/write, output с корректной трактовкой reasoning и tool charges. Tier, длинный контекст и валюта фиксируются; неизвестный компонент делает соответствующий итог неизвестным, а не бесплатным.

Subscription использует отдельную относительную шкалу нагрузки и при наличии явно наблюдённые quota pools/остатки/reset. Defaults не обещают преобразование tokens → проценты подписки. Для подтверждённого преобразования допускается оценка upper usage относительно остатка; одинаковый pool не клонируется на каждую модель. API usage, относительная subscription load и время имеют отдельные редактируемые значения или множители для каждой модели/harness, фазы и supported effort, со своими единицами и provenance на уровне записи. Defaults не вычисляют эти таблицы из единой для всех моделей кривой effort; одинаковые оценки допустимы при явном основании. Переключение или изменение качества не изменяет resource-настройки автоматически. Эти величины не переводятся в шкалу качества 0–100: множитель, токены, деньги, время и относительная нагрузка подписываются своими единицами. Неизвестный ресурс остаётся unknown, а не нулём. Численное значение без сопоставимого измерения помечается heuristic или proxy по правилам происхождения.

Observation time и as-of time — явные входы. Evaluator не читает часы: истечение observation определяется по переданному as-of, включённому в digest. Неизвестный остаток не мешает относительному рейтингу и отображается как unknown.

### 7. Размещение внутри change и archive

Выбранная структура:

    <changeRoot>/
      assessment/
        profile.json
        latest.json
        runs/<assessment-id>/
          profile.json
          config.snapshot.json
          benchmarks.snapshot.json
          manifest.json
          report.json
          report.md

assessment-id — SHA-256 canonical profile + effective config + referenced benchmark snapshot + version identity. Version identity включает версии evaluator, renderer, schemas и правил нормализации, влияющих на результат; любое изменение их семантики меняет identity. Сначала формируется и валидируется полный run во временном sibling-каталоге внутри assessment; затем он становится завершённым snapshot. Только после этого атомарно меняется latest.json. Повтор тех же входов проверяет имеющийся run и переиспользует его. Изменённые входы создают новый run. profile.json — рабочая текущая версия; profile.json внутри run immutable. При сбое допускается незавершённый temp-каталог, но он не становится latest и не повреждает историю.

Manifest хранит версии schema/evaluator/renderer и digest входов/выходов. Время выполнения и абсолютный путь машины не входят в canonical report. Относительные пути артефактов считаются от changeRoot, исходников — от явно заданного repo root; evidence может дополнительно ссылаться на Git revision. Исходные документы целиком в snapshot не копируются.

OpenSpec archive должен перенести весь assessment вместе с change. Это проверяется отдельным integration fixture реальным поддерживаемым CLI: успешный archive, сохранение файлов и digest, read-only replay из нового расположения. До такой проверки поведение конкретной версии CLI не считается принятым.

Replay проверяет manifest и использует snapshot. Он не требует старых исходников и не переписывает архив. Несовместимый evaluator сообщает нужную версию; выполнять произвольный код из snapshot запрещено. При необходимости пользователь устанавливает соответствующий release пакета. Freshness — отдельная проверка текущих источников и config: исторический replay не равен подтверждению актуальности evidence.

Альтернатива «профиль только в глобальном skill-каталоге» отклонена требованием владельца. Простая перезапись единственного profile без history не позволяет сравнить план и факт. Custom OpenSpec schema для v1 не требуется: assessment — дополнительные versioned-файлы change; обязательный artifact gate или автоматический hook не предполагается.

### 8. Интеграция и интерфейс

CLI предоставляет assess, validate-profile, check-freshness, replay и configure. Конкретное имя executable закрепляется вместе с package metadata. assess разрешает change через OpenSpec status/context, сохраняет выбранный store и использует возвращённый changeRoot. Нет root — сообщение об ошибке, без неявного init. Нет однозначного change — выбор пользователя. Перед verify формируется новый профиль по фактическому diff.

Общий SKILL.md описывает ручной вызов после propose и перед verify, ссылки на rubric и запуск CLI. Автоматическое выполнение именно после propose требует настройки workflow проекта; v1 документирует такую точку вызова и не обещает несуществующий универсальный hook. Generated upstream skills не патчатся. Подключение пакета к трём клиентам документируется после проверки их текущих механизмов discovery; копии должны содержать одинаковый version/digest, а не независимые форки.

Конфигуратор — локальная browser-страница с матрицей, пояснениями и preview через тот же pure evaluator. Небольшой Node HTTP server привязывается к loopback на свободном порту и отдаёт только пакетные assets. Входы выбираются пользователем; изменения экспортируются как JSON, HTTP API произвольной записи файлов не нужен. Нет CDN, внешних fonts, analytics и inference. Такой интерфейс сохраняет простоту редактирования без отдельного backend или SDK.

### 8.1. Подписи, шкалы и выбор effort

Колонка phase relevance weight в обеих фазах подписана «Вес» с кнопкой ⓘ. Ширина определяется коротким заголовком и числовым полем, а не полной фазовой подписью. Доступные имена полей сохраняют полное назначение для реализации или проверки. Подсказка начинается с «Вес параметра для реализации» либо «Вес параметра для проверки» и объясняет: «При одинаковой сложности параметр с весом 2 вносит вдвое больший вклад, чем с весом 1. Вес 0 исключает параметр из взвешенной оценки, но не отменяет обязательные ограничения». Пояснение также сохраняет связь с уровнем сложности из профиля и формулой relevance; вес, сложность и оценка модели не смешиваются.

Подсказка веса открывается по наведению, keyboard focus и нажатию на ⓘ. Она располагается отдельной панелью поверх таблицы вне обрезающей области её прокрутки, ориентировочно шириной 300 px с ограничением по доступной ширине экрана. Обычный шрифт и переносы строк обеспечивают читаемость; панель не наследует ширину узкой колонки или запрет переноса из заголовка. При горизонтальной прокрутке и у краёв экрана положение удерживает всю панель в видимой области. Escape закрывает открытую панель; кнопка и пояснение остаются доступны с клавиатуры.

Модельная ячейка имеет подпись/доступное имя «Оценка модели · 0–100» с моделью, фазой, параметром и effort. Пояснение определяет пригодность для этой комбинации и прямо говорит, что это не вероятность успеха. Ввод, подсказки и читаемый отчёт показывают модельные оценки в диапазоне 0–100, без знака процента, максимум с двумя десятичными знаками и без лишних конечных нулей. Примеры: 8200 bp → 82; 8201 bp → 82.01. Порог качества в том же сравнении отображается в той же шкале. JSON сохраняет целые bp с явно документированной единицей; уровень сложности профиля 0–4 не преобразуется.

Адаптер ввода разбирает десятичную запись точно в целое число bp, без скрытого округления или вычисления ранга по отображаемой строке. Выход за 0–100, лишняя точность, неконечное или неоднозначное значение дают ошибку. Unknown отображается placeholder «Нет данных» и индикатором u. В допускающих unknown полях качества и resource-оценок очистка поля, включая пробельный ввод после trim, при завершении редактирования сохраняет null/unknown с прежним основанием отдельно. Число 0 остаётся числом; непустой неверный ввод является ошибкой. Удаление текста не означает удаление override или возврат default. Отдельные кнопка ∅ и меню «Нет данных» отсутствуют; подсказка сообщает «Очистите поле, если данных нет». Обязательные числовые настройки, включая веса и параметры политики, сохраняют свою валидацию и не становятся nullable.

В заголовке каждой модели находится независимый селектор отображаемого effort. Он управляет только просмотром и редактированием выбранной колонки; allowed efforts для рейтинга настраиваются отдельно. Простое переключение просмотра не меняет effective config, input digest или рейтинги. Это позволяет одновременно сравнить Astra medium и Sol high. Действие «Все уровни» открывает для одной модели таблицу factor × supported effort текущей фазы; каждое значение имеет собственный индикатор происхождения.

Список «Разрешены для рекомендаций» оформляется выпадающим multiselect с чекбоксами только для supported efforts данной модели. Свёрнутый контрол перечисляет выбранные IDs через запятую в порядке supported efforts, в том числе при выборе всех уровней. Его ширина ограничена колонкой: длинный текст сокращается многоточием, полный список доступен при наведении и фокусе. Меню остаётся открытым при нескольких переключениях, закрывается по Escape или клику снаружи и поддерживает работу с клавиатуры. Открытие меню и закрытие без изменения выбора не меняют конфигурацию; изменение набора влияет только на разрешённые варианты этой модели и связанные результаты preview, не переключая effort просмотра и не изменяя quality/resource-записи.

Последний выбранный effort снять нельзя: действие отклоняется с сообщением «Выберите хотя бы один effort», прежняя галочка и список сохраняются. Это предотвращает существующую неоднозначность, при которой пустой список сбрасывает ограничение и возвращает все уровни. Выбор всех supported efforts может сохраняться прежним способом без явного ограничения; новый UI не создаёт пустой выбор. Полностью выключить модель можно через enabled. Формат данных и семантика отсутствующего ограничения не меняются из-за замены контрола.

### 8.2. Компактное происхождение и доступность

Вместо длинного chip у каждого коэффициента используется круг диаметром ориентировочно 18–20 px с одной строчной буквой. Общая легенда расположена над матрицей:

| Буква | Статус | Значение |
| --- | --- | --- |
| p | proxy | Оценка через косвенные данные с явным mapping |
| h | heuristic | Эвристическая оценка |
| o | user-override | Пользовательское значение |
| u | unknown | Нет данных |
| m | measured | Сопоставимое измерение |

Наведение и keyboard focus показывают полное название и краткое основание; нажатие открывает карточку provenance из раздела 4. Управление доступно с клавиатуры и имеет полную доступную подпись. Цвет является дополнительным признаком, буква сохраняется во всех темах. Круг остаётся компактным; при необходимости область нажатия больше видимого круга. Индикатор относится к текущему effort-значению и не заменяет отдельный статус доступности модели. В config, snapshots и машинных отчётах сохраняются полные status IDs, без сокращения до букв.

### 8.3. Числовой ввод ресурсных множителей

В редактируемом поле ресурсного множителя находится только число: 0.6, 1.2 или 0.78 вместо ×0.6, ×1.2 и ×0.78. Подпись строки и доступное имя сохраняют смысл множителя и единицы ресурса. Форматирование не добавляет лишних конечных нулей. Префикс × не является частью ввода и не принимается как допустимый числовой текст.

UI допускает цифры и один десятичный разделитель — точку или запятую. Запятая нормализуется в точку; обе записи точно преобразуются в прежнее целочисленное представление без изменения единиц или скрытого округления. Диапазон остаётся 0–100 включительно, точность — до четырёх знаков после разделителя. Эти правила относятся к ресурсным множителям и не меняют отдельную двухзначную точность quality-оценок.

Недопустимые символы блокируются при вводе, а не только после ухода из поля: буквы, ×, знаки +/−, экспонента и повторный десятичный разделитель не попадают в редактируемый текст. Некорректная вставка отклоняется целиком с сохранением текста и значения; нельзя вырезать буквы из «1abc2» и получить 12. Ограничение не мешает навигации, выделению, удалению, стандартным командам копирования/вставки допустимых чисел и последовательному набору дроби. Пока пользователь набирает число, допустимы промежуточные состояния вроде «1.»; это не основание для сохранения неполного числа или неявного создания unknown.

При завершении редактирования остаётся независимая проверка формата, диапазона и точности; ошибочный непустой ввод не меняет сохранённое значение и не округляется. Очистка, включая пробельный ввод при итоговой обработке после trim, сохраняет unknown/null с прежней записью отдельно и индикатором u; 0 остаётся числом. Export/import и preview используют прежние числовые значения и provenance; миграция формата данных из-за этих UI-правок не требуется.

### 9. Проверки и подготовка к распространению

Meaningful tests: одинаковые canonical bytes при перестановке JSON keys и клиента; stable ties; изменение model weights не меняет change complexity; неизвестное не равно нулю; запрет неподдерживаемого effort; корректный учёт cache/reasoning; влияние common quota pool; overrides сохраняют 0/false; failure оставляет latest; archive/replay сохраняют историю. Новая политика дополнительно проверяется на росте C выше прежних anchors, точных дробных поправках, границах времени 29/30/31/45/60/90 минут, неизвестных ресурсах/времени, одинаковом comparator efforts и моделей, отсутствии влияния лишнего качества на первичный расход и неизменности budget/quota checks.

Публичный example содержит небольшой искусственный change, evidence-профиль, config и golden report. Документация объясняет formula, assumptions и benchmark coverage. CI запускает offline-проверки на поддерживаемых Node/OS, а integration с закреплённым OpenSpec проверяет реальный archive. Проверки не требуют платных моделей и credentials.

Для доработок обязательны проверки полной effort-матрицы и explicit unknown; отсутствия fallback и ограничения монотонности; независимости качества и расхода; изоляции редактирования ячейки; сохранения provenance при override/reset и смене модели. Проверяются точный round-trip 0, 82, 82.01 и 100, отклонение лишней точности, прежние численные результаты при одной только смене отображения и неизменность рейтинга при смене effort для просмотра. UI-проверка охватывает легенду, полное доступное имя, tooltip/focus и открытие источников с клавиатуры. Миграция проверяется отдельно на старых конфигурациях с byEffort override, delta, clamping и unknown; новые baseline-оценки не смешиваются с проверкой сохранения результата. Smoke test discovery трёх клиентов проверяет подключение общего пакета; платные inference прогоны не являются скрытым требованием тестов.

Для раздела 11 отдельно проверяются multiselect мышью и клавиатурой, свёрнутый список и ограничение его ширины, запрет снятия последнего effort, независимость allowed efforts от просмотра и model records. Проверка подсказки веса проводится в браузере, включая узкое окно и горизонтальную прокрутку. Для множителей проверяются точка/запятая, точный round-trip 0/0.6/0.78/1.2/100 и четырёх десятичных знаков, блокировка символов, отклонение вставки целиком и сохранение обычного редактирования дроби. Отдельно проверяются диапазон, лишняя точность, unknown/0, provenance, reset/export/import и неизменность численных результатов UI/CLI при одинаковых входах. Прежние проверки разделов 1–10 не подменяют приёмку новых UI-требований.

## Risks / Trade-offs

- [Профиль зависит от семантического суждения агента] → фиксированные якоря, evidence, видимые unknown и сохранённый input; обещание детерминизма ограничено расчётом.
- [Для всех десяти моделей нет полной независимой матрицы] → provenance на уровне коэффициента, explicit proxy/heuristic и coverage; никаких придуманных измерений.
- [Aggregate coding score плохо переносится на verify] → отдельная phase matrix, documented mapping и последующая локальная калибровка.
- [Расход подписки непрозрачен] → относительная нагрузка по умолчанию, отдельные observations и отсутствие обещаний точных процентов.
- [Snapshot увеличивает change] → сохранять только используемые структурированные records и effective config; не копировать datasets и полные исходники.
- [Обновление схемы или evaluator меняет результат] → versioned contracts, immutable snapshots и явная несовместимость при replay; миграция формата и намеренная смена policy проверяются отдельно.
- [Округление малого расхода скрывает штраф времени] → точный рациональный критерий S, округление только отображения.
- [Скорректированный расход принимают за сумму оплаты] → исходные прогнозы и штраф показываются отдельно; бюджет проверяется по исходным значениям.
- [Подключение skills отличается между клиентами] → один source package и проверяемые инструкции подключения; generated OpenSpec skills не модифицируются.

## Migration Plan

Исходный config v1 использовал base/effortDelta и optional byEffort; реализованный v2 хранит отдельные effort-записи. Их преобразование является миграцией формата при неизменной политике выбора. Включение minimum-resource-with-time-penalty — отдельное семантическое изменение config/report contracts с явным policy ID и новой evaluator/version identity; изменения читаемого отчёта получают renderer identity. Импорт прежнего формата сообщает о необходимости явной миграции, а не трактует старые числа в новой единице или молча меняет алгоритм.

Миграция формата v1 → v2 выполняется только по отдельному действию пользователя над рабочей конфигурацией: сначала собирает старый effective config из выбранных старых defaults и overrides по старым правилам, затем материализует каждую поддерживаемую комбинацию. Приоритет сохраняется точно: явный byEffort, иначе clamp(base + effortDelta, 0, 10000); неизвестный base остаётся unknown, отсутствующая delta в старой версии равна нулю. Сохраняются все enabled/allowed effort настройки, цены, ресурсы, ограничения, веса и preferences. Составное значение base + эвристическая delta помечается heuristic с описанием переноса и исходным provenance; сам перенос не создаёт новых измерений. Прямые записи byEffort сохраняют применимое происхождение.

Для миграции только формата при неизменных смысловых входах и прежней политике проверяются прежние численные scores, ресурсы и порядок кандидатов до и после преобразования; обновление baseline по новым данным выполняется отдельно. Новый формат и version identity дают новый digest и могут изменить bytes отчёта, поэтому побайтовое равенство с новым run не обещается. Смена только UI-шкалы не меняет численный расчёт. Миграция выдаёт отдельный результат для review/export и не перезаписывает исходную конфигурацию без явного действия.

Переключение со старой utility на новую политику выполняется явно над рабочей конфигурацией и намеренно может менять выбор модели/effort. Оно сохраняет профиль, качество и его пороги, исходные resource-прогнозы, availability, budget/quota и пользовательские overrides, но заменяет правило экономического сравнения и его настройки. Старые quality/economy/time weights и anchors не преобразуются в новые параметры неявно и не остаются скрыто активными; переход явно предлагает согласованные defaults g = 30, s = 30, k = 0.05. Импорт старой конфигурации показывает её policy/version и необходимость явного перехода, а не выдаёт старый режим за новую оптимизацию. Равенство рейтингов при смене policy не является критерием миграции; проверяются сохранность исходных оценок, новый расчёт по формуле и отдельный run с новой identity.

Исторические runs, manifests и latest не мигрируют при открытии конфигуратора или replay. Старый snapshot воспроизводится совместимой версией evaluator; иначе система указывает нужную версию. При новом assess сохраняется отдельный run по новым входам. Rollback миграции использует сохранённые старые config/overrides и совместимый release, без удаления новых или старых snapshots.

После offline и archive integration checks проверяется подключение трёх клиентов. Отсутствие установленного клиента/CLI оставляет соответствующий smoke discovery непроверенным, но не блокирует независимые schema/evaluator/UI задачи. Публичная публикация выполняется отдельно; подготовленный пример пригоден для будущей статьи.

Rollback установки — отключить подключение пакета в клиенте. Уже сохранённые assessment остаются в changes и archive. Применение rollback не удаляет историю и не переключает модели.

# Формула расчёта (evaluator 3, renderer 3, normalization 1, policy minimum-resource-with-time-penalty v1)

Все величины хранятся целыми числами: оценки моделей и индексы — basis points 0–10000, деньги — микроединицы валюты, скорректированный расход S — точная дробь целых чисел. Произведения и деления идут через BigInt с одним правилом округления — **вниз** (`floor`). NaN, Infinity, дробные числа и дублирующиеся JSON-ключи отклоняются. Ключи сериализуются в порядке UTF-16 code units (не `localeCompare`), поэтому вывод не зависит от locale, часового пояса, порядка ключей и клиента.

## Три разных числа

| Число | Где задаётся | Шкала | Смысл |
| --- | --- | --- | --- |
| Уровень сложности параметра `d_i` | профиль change (агент) | 0–4 по якорям rubric | насколько трудна эта сторона **change** |
| Важность параметра `w_i` («Важность параметра для реализации/проверки») | `phases.<phase>.relevanceWeights` | целое ≥ 0 | относительный вклад параметра при сравнении моделей; вес 2 даёт вдвое больший вклад, чем 1, при той же сложности; 0 исключает параметр из взвешенной оценки, но не отменяет критические ограничения |
| Оценка модели `c_i` («Оценка модели · 0–100») | `models[].quality[phase][effort][factor]` | хранится 0–10000 bp, показывается 0–100 | пригодность **модели** при данном effort для этого параметра и фазы; не вероятность успеха |

Отображение: 8200 bp → `82`, 8201 → `82.01`, 10000 → `100` (до двух знаков, без лишних нулей и без знака процента). Ввод разбирается точно в целые bp: больше двух знаков, значения вне 0–100, знаки, экспоненты и пустая строка отклоняются без округления; отсутствие данных — отдельное состояние «Нет данных» (`value: null`, `status: unknown`). Пороги качества в отчёте показываются в той же шкале. Сортировка всегда идёт по целым bp, а не по отображаемой строке.

## Порядок

1. Проверить profile, effective config, benchmark snapshot, provenance коэффициентов и `asOf`.
2. Свойства change (только profile + `complexityRules`): уровни факторов, индексы `volume`/`complexity`/`risk`/`uncertainty`, категория нагрузки (`xs`…`xl`) для low/typical/high, требование к качеству `demand = max(upper(complexity), upper(risk))`.
3. Для каждой фазы (`apply`, `verify`) и режима (`api`, `subscription`) развернуть enabled model + harness во все разрешённые effort (`efforts` ⊆ `supportedEfforts`; неподдерживаемый effort — ошибка конфигурации).
4. Ограничения: `enabled`, `availability`, `minContextTokens`, `requiredCapabilities`, API-бюджет, известная нехватка квоты. Нарушение → исключение; неизвестное значение для обязательного ограничения → `provisional`.
5. Пригодность, порог качества, критические факторы, ресурсы, экономическое сравнение (S; для legacy-конфигураций — utility).
6. Сортировка вариантов, выбор одного effort на кандидата, четыре списка, trace.

## Пригодность (heuristic fit score)

Для применимых факторов с уровнем `d_i` (для `unknown` — консервативный уровень), весом фазы `w_i` и коэффициентом модели `c_i`:

```
r_i = w_i × max(1, d_i)
F   = floor( Σ r_i × c_i / Σ r_i )        (только по r_i > 0)
```

- `not-applicable` исключается; неизвестный активный `c_i` не заменяется нулём: `F` не вычисляется, показываются известные вклады и `coverage = floor(10000 × Σ r_known / Σ r)`, кандидат — `provisional`.
- `Σ r = 0` (все применимые веса фазы нулевые) → рейтинг `undefined`, список не строится.
- Коэффициент варианта — **ровно** запись `quality[phase][effort][factor]` (config schema 2). Нет `base + effortDelta`, интерполяции и заимствования у соседнего effort: отсутствующая запись — ошибка конфигурации, отсутствие данных — явная запись `unknown`. Одинаковые и немонотонные значения разных efforts допустимы и используются как есть.
- Trace и `contributions` называют точную запись (`record: {phase, effort, factor}`), её значение, статус, `sources` (выводят число), `support` (лишь подтверждают предположение), `inheritedFrom`, `origin` (исходная запись до пользовательского изменения) и `migrated`.
- Ресурсы варианта читаются из `resources.api.usage`, `resources.subscription.load`, `resources.time.minutes` того же phase/effort; изменение оценки качества их не меняет.
- Порог качества: последний `qualityFloors[k]` с `fromDemandBp ≤ demand`. `F < floor` → `below-threshold`.
- Критические факторы (`criticalFactors`): если верхняя граница уровня ≥ `whenLevelAtLeast`, коэффициент должен быть ≥ `minCoefficientBp`; иначе `below-threshold` (низкая цена этого не компенсирует), неизвестный коэффициент → `provisional`.

`F` — эвристическая оценка соответствия, **не вероятность успеха**.

## Выбор: дешевейший достаточный вариант (policy `minimum-resource-with-time-penalty` v1)

Порог качества и критические параметры — обязательные условия допуска. Среди вариантов, которые их прошли, предпочтителен вариант с наименьшим скорректированным расходом:

```
over = max(0, T − g)
S    = C × (1 + k × over / s)
```

| Обозначение | Смысл | Default |
| --- | --- | --- |
| C | верхний прогноз исходного расхода: API `highMicros` (микроединицы валюты) или нагрузка подписки `highLoad` (относительные единицы) | — |
| T | типичный прогноз времени `typicalMinutes`; верхняя оценка времени показывается отдельно как риск задержки, но не подменяет T | — |
| g | время без штрафа, минут: до g включительно T не влияет на S и не участвует даже в tie-break | 30 |
| s | интервал начисления, минут, > 0 | 30 |
| k | надбавка за интервал (`rateBp` / 10000); 0 явно отключает учёт времени | 0.05 (500 bp) |

При defaults: 0–30 мин → ×1, 31 → ×601/600, 45 → ×1.025, 60 → ×1.05, 90 → ×1.10, 150 → ×1.20 — линейно и непрерывно, без округления числа интервалов и без сложных процентов. Пример: C = 10 USD, T = 60 мин → S = 10.5 USD для сравнения, а прогноз оплаты и проверка бюджета остаются 10 USD.

- S вычисляется **точно**: числитель `C × (10000·s + rateBp·over)`, знаменатель `10000·s`, сравнение — перекрёстным умножением BigInt. Нет якорей, насыщения 0–10000 и предварительного округления: рост C при равном T всегда ухудшает S (в том числе выше прежних 20 USD или 1000 единиц нагрузки), разница 1/600 при C = 1 не превращается в tie. В отчёте S хранится как `{ numerator, denominator }` (десятичные строки); отображение округляется отдельно.
- Добавление другого кандидата не меняет индивидуальный S.
- Неизвестный C, или неизвестный T при k > 0, даёт неизвестный S: ноль, «30 минут» или «без штрафа» не подставляются. При k = 0 время не требуется. Известные C = 0 и T дают S = 0.
- S — **критерий сравнения**, а не цена и не списание квоты. API-бюджет и проверки квоты используют исходные прогнозы.
- Параметры задаются отдельно для API и подписки (`selection.api.timePenalty`, `selection.subscription.timePenalty`) и не заменяют важность параметров пригодности.

### Legacy policy `weighted-utility`

Конфигурации, перенесённые `migrate-config` из v1/v2, сохраняют прежнее правило 0.1/0.2, пока пользователь явно не выполнит `switch-policy`:

```
N(x, anchor) = min(10000, floor(10000 × x / anchor))
U = floor( (q·F + e·(10000 − N(resource_high)) + t·(10000 − N(time_high))) / (q + e + t) )
```

Его веса и якоря не действуют под новой политикой (в config schema 3 они там запрещены).

## Сортировка

Группы: `eligible` → `provisional` → `below-threshold`; исключённые — отдельным списком по ID.

- `eligible`: сначала варианты с известным S — по возрастанию точного S, затем исходного C, затем по убыванию F; потом варианты без S (по убыванию F) с пометкой отсутствующего экономического сравнения. Под legacy-политикой вместо S — utility по убыванию, затем F, затем `resource_high`.
- Тот же comparator выбирает effort модели и сравнивает модели между собой: более низкий effort рекомендуется, если его качества достаточно и S меньше; избыточное качество не компенсирует больший S.
- `provisional`: сначала с известным `F` (по убыванию), затем без `F`.
- `below-threshold`: по убыванию известного `F`.
- Последний ключ всегда — candidate ID (`harness/modelId`), затем effort, в порядке code units.

Рекомендуемый effort кандидата — первый его вариант по тем же правилам. Статус рейтинга: `ok` (есть eligible с известным S; первый — вершина списка для ручного выбора), `economics-undefined` (качество достаточно, но S не определён ни у одного варианта — экономической рекомендации нет), `provisional-only` (ничего не подтверждено), `no-suitable` (никто не проходит порог и ограничения), `undefined` (все веса нулевые).
